## Deploying a model: `x2c deploy`

One command takes a model from its IR to a verified deployment bundle for the BM Labs chip
(sky130-reram-fpga: 2 × X2 32×32 crossbars + FABulous eFPGA). It runs at 4-bit cells and a 14 MHz clock.

```
x2c deploy --workload mobilenetv2
x2c deploy --workload deepgate          # real INT8 weights + requant from BMsemi_Model
x2c deploy --workload mnist
x2c deploy --workload mobilenetv2 --sim   # Linux (Icarus): every layer also on the 1-bit engine RTL
```

### What the agents do

| step | who | what |
|---|---|---|
| 1 | inputs | IR from BMsemi (compiler-V2 graph / chain workload), or `--ir file.json` |
| 2 | A1 | partition (matrix ops → X2) + X2 tile schedule over both blocks; LLM proposals only if validated (`--llm none` = baseline + code schedule) |
| 3 | `src/x2c/compiler/int8_net.py` | INT8 network. Module kinds are INFERRED from structure: BN after a matrix op, ReLU6 after BN, which gives 16 + 11 on the real graph. BN is folded into the bias, ReLU6 becomes a clamp to [0,127], residual add saturates, global average pool |
| 4 | executors | every tensor is compared with an independent nested-loop golden model. 4-bit X2 Python model; `--sim`: 1-bit two-block engine in Icarus |
| 5 | A4 tools | chip status, engine bitstream, missing X2 facts |
| 6 | bundle | `deploy/<workload>/` |

How a model reaches the X2: the X2 takes only uint8 inputs. A signed tensor goes in as x+128, and the host subtracts
(128 + model zero point)·ΣW. This is exact integer arithmetic, and padding uses the same zero point.

### The bundle

| file | contents |
|---|---|
| `plan.json` | A1's partition and schedule (resident layers, policy, latency) |
| `host_program.json` | the ordered steps: X2 layers (input tensor, offsets, epilogue bias/shift/clamp or the repo's requant), adds, pool |
| `x2_program.npz` | per layer and tile: the 32×32 cell levels (0..15) and the placement |
| `expected.npz` | every intermediate tensor from the golden model (input → output) |
| `engine/` | `x2_engine2_4bit.bit` + `design.pcf` (pin map) + audit. The **same bitstream for every model**; a model is deployed by programming the cells and running the host program |
| `report.json` | checks, A1 schedule, 1-bit cycles, missing facts, evidence level |

### Results

| workload | X2 layers | 4-bit exact | 1-bit engine RTL | A1 schedule |
|---|---|---|---|---|
| MobileNetV2 (real graph, seeded weights) | 17 (21 steps) | all 21 | all 17 layers exact, 4,295,897 cycles measured vs 4,296,056 predicted | 254 ms, 46 % below single-block |
| MNIST edge filter (stand-in data) | 1 | yes | full 28×28 exact, 461,564 cycles | 32.8 ms |
| DeepGate (stand-in data) | 10 | all | 2 small layers simulated; 8 over `--max-tiles` (640 1-bit tiles each) stay on the 4-bit path | 13.8 s: weights cannot stay resident, so reprogramming dominates |

With BMsemi_Model, the DeepGate check also requires our golden chain to equal the repo's own `fwd` chain, and MNIST requires
it to equal the repo's `edge_filter` map.

### Still assumed or missing (reported in every `report.json`)

- `cell_compute_4bit`: the 4-bit cell rule sum(pwm·level) is ASSUMED. The chip's X2 model is 1-bit only. Fill it in via `specifications/x2_overrides.json`.
- 4-bit cell programming commands (WRITE_LEVEL) are not in the chip's command set. `x2_program.npz` therefore stores levels, not commands.
- `silicon_variation`: unknown. Every check is exact digital simulation.
- MobileNetV2 weights are random seeded INT8 because the compiler artifact has shapes only. To use real weights, pass a model with weights.
- Evidence: Python X2 model + RTL simulation with the BM behavioral X2. NOT the configured fabric, NOT silicon.

## The partition on the chip

`specifications/hardware_config.json` v1.0 is generated by `x2c chip config` from `chip_profile.json`.
The previous file is kept as `hardware_config.compiler_v2.json`.

### Two views of every plan
| View | Geometry | Purpose |
|---|---|---|
| compiler (`plan.totals`, `x2_tiles`) | 64-row PE, `hw["compiler_v2"]` (BMsemi `core/mapping.py` PEGeometry default, the "YOLO26 / FP4LLM" PE) | proves the compiler artifact is read correctly: still must equal `compiler_expected_tiles` (24 for tiny MobileNetV2) |
| chip (`plan.chip`) | 32 x 32, 1-bit cells, 2 blocks (sky130-reram-fpga) | what the real X2 needs |

### Chip numbers and where they come from
| Field | Value | Source |
|---|---|---|
| `x2.rows/cols` | 32 x 32 | `RERAM_CIM_32x32.v` ROW_INDEX0-4 / COL_INDEX0-4; `cim32x32.sv` l.484 `array_state [0:31]` |
| `x2.blocks` | 2 | `.FABulous/bel.txt` l.899 (X20Y6), l.2068 (X20Y14) |
| `x2.cell_bits` | **4 (decision, 2026-11-13)** | follows BMsemi `deep_gate/Crossbar_array.py` l.127, 165 (4-bit banks). The chip repo's model computes with 1 bit (`cim32x32.sv` l.802, 847-848); `x2c chip config --cell-bits 1` models that |
| `x2.timing_cycles` | read 160, program 360, compute 450 | `cim32x32.sv` l.14-16 (behavioral model, not silicon) |
| `weights` | signed INT8, 2 sign banks x 2 four-bit banks = 4 cells (16 with 1-bit cells) | BMsemi `deep_gate/Crossbar_array.py` l.29-30, 127, 165 |
| `efpga` | 2160 LC, 18 MACC, 36 RAM32x4, 4 GBUF, 36 pins | `bel.txt` BEL counts; team: all[0..27] are example pins |

Open question for the team: is the silicon cell 4-bit (as configured, following DeepGate) or 1-bit (as the chip's
behavioral model computes)? 4-bit plans cannot be checked in the chip's behavioral simulation, which is binary.
The tests run every chip check with both cell sizes.

### How layers map onto the X2
* taps `(C/groups)*R*S` -> rows; outputs x 16 cells -> columns (bit planes and sign banks are separate columns,
  combined afterwards by shift-and-add).
* Grouped and depthwise convs: each group has its own inputs, so groups share a tile only on separate rows AND
  separate columns (block-diagonal; unused cells stay RESET = 0).
* The planner writes the exact placement (`plan.chip.layers.<layer>.placement`). `validate_partition` checks any
  placement independently (inside 32 x 32, no shared rows or columns within a tile, every weight cell exactly once)
  and recomputes every chip total from it.

### Schedule and cost
* More tiles than blocks: layers are either **resident** (programmed once) or **streamed** (reprogrammed every
  inference). If anything is streamed, one block must stay free to stream into, so 1 block can be resident.
* The baseline picks the resident set that saves the most programming (`chip_x2.best_resident_set`). A1 can propose
  another resident set and schedule, which code validates (see [agents.md](agents.md#a1-the-x2-schedule)).
* Cycles: compute = per MVM 32 beats + COMPUTE_DELAY + 32 results (lower bound); programming = every weight cell
  SET once at PROGRAM_DELAY (upper bound; the true count depends on weight values).
