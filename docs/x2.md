## X2 golden model: `x2c sim x2`

`src/x2c/chip/x2_golden.py` is a Python model of ONE X2 block (`sky130_bmlabs_reram__cim32x32`), written
from the BM Labs behavioral model in the chip repo and checked against it in Icarus Verilog.
It models what the block returns (mode, column, count, last), not cycle timing.

### What the X2 computes (from the behavioral model)
| Command | Result |
|---|---|
| COMPUTE (one beat per row, last beat has `compute_last`) | per column: `sum(pwm[row] for selected rows where cell(row, col) is SET)`, clamped |
| READ | `cell level + pwm`, clamped |
| SET / RESET | cell state 1 / 0, level = `((t1 + t2) >> 1) + pwm` (mod 2^14); returns `level + pwm of the previous READ`, clamped |

* Clamp ceiling = `(TDC_TIME_OUT[5:0] << 8) | 0xFF`.
* COMPUTE columns: all 32 with `compute_all_columns`, otherwise the set of beat columns; emitted
  in ascending order, `last` on the highest.
* Same row twice in one stream: the later pwm wins. A non-COMPUTE command cancels an unfinished stream.

### Consequences for the compiler (findings, not assumptions)
1. **Weights are binary.** COMPUTE uses only the SET/RESET state; the 14-bit level does not enter
   COMPUTE. A multi-bit (e.g. INT8) weight therefore needs several cells or several passes
   (bit slicing), plus a scheme for signs. How the team wants this done is a team decision.
2. **Inputs are unsigned 8-bit** (pwm 0..255).
3. **Saturation:** a full 32-row sum is at most 32 x 255 = 8160. It fits only if
   `TDC_TIME_OUT >= 31` (ceiling 8191). With all parameters 0 (as in the chip repo's
   `reram_cim_32x32` example design) the ceiling is 255.

### Check
`x2c sim x2 --sim` (Linux) writes 4 scenarios to `chip_build/x2_check/`, simulates the
behavioral model with `hardware/sim/x2_vector_tb.sv`, and compares every result with the golden model.

| Scenario | Covers |
|---|---|
| directed | each rule once |
| binary_matmul_32x32 | full array, 0/1 weights, `y = x @ W` for 4 vectors (also checked with plain Python) |
| zero_parameters | all parameters 0: ceiling 255, saturation |
| random_mixed | 120 random operations with random parameters (53 saturated results) |

`tests/test_x2_golden.py` replays bundled simulator logs (`tests/fixtures/x2_check/`) so it runs
without Icarus, and plants 9 bugs in the golden model to show the logs catch each of them.
`test_fixture_was_recorded_from_this_model_version` fails if the chip repo's model changes.

### Not covered
* Timing (delays, dead time) and error codes; the checker compares values and order only.
* Analog behavior (the behavioral model does not simulate it).
* The X2 inside the configured fabric (that needs the fabric simulation).

## Weight packing: `x2c sim pack`

`src/x2c/compiler/x2_pack.py` turns one matrix layer into what the X2 receives and rebuilds the layer output from the
X2's 14-bit column counts. `x2c sim pack` checks it end to end.

| Part | What it does |
|---|---|
| `weight_columns` | signed INT8 -> positive/negative banks (BMsemi deep_gate `Crossbar_array.py` l.29-30), each split into `cell_bits` digits (l.127, 165): 4 cells per weight with 4-bit cells, 16 with 1-bit |
| `pack_layer` | places blocks exactly like the partition (`chip_x2.place_groups`), fills each 32 x 32 tile, and refuses a layer whose worst-case COMPUTE could pass the 14-bit cap (16383) |
| inputs | each 8-bit input is sent as 4-bit slices (two COMPUTE passes) with 4-bit cells: 32 x 15 x 15 = 7200 fits; one 8-bit pass would reach 122400 |
| `program_commands` | the commands that change the block's cells into a tile's cells (only changed cells). 1-bit: SET / RESET, the chip's own commands. 4-bit: `WRITE_LEVEL`, which is NOT a chip command (the chip repo's X2 stores 1 bit) |
| `compute_beats` | one COMPUTE beat per used row, pwm = that row's input slice, `compute_all_columns` |
| `recombine` | `y = sum(2^(p*4) * sign * 2^(d*cell_bits) * count)`, adding row folds of the same columns |
| `required_tdc` | smallest TDC_TIME_OUT whose ceiling `(t << 8) | 0xFF` covers the layer's worst count (data dependent; 28 covers any full 32-row tile with 4-bit cells and 4-bit slices) |

Execution: 4-bit streams run on `MultiLevelX2` (a model of the 4-bit decision, checked against NumPy only).
1-bit streams run on `x2c.chip.x2_golden.X2Golden` and, with `--sim`, on the BM Labs X2 behavioral model in Icarus.

Evidence: conv, depthwise, pointwise and linear layers with random INT8 weights, both cell sizes:
outputs equal NumPy exactly; the 1-bit streams on the BM Labs X2 model (Icarus) also equal NumPy exactly.

ASSUMED: patch order c-r-s. Not covered yet: stride/padding im2col (the packing works on patch vectors), and the
fabric side that sends these commands is the [host bridge](#host-bridge-x2c-sim-bridge).

## Recombiner: `x2c sim recombine`

The X2 returns 14-bit column counts. To get a layer's real output, the eFPGA adds them back up:
`acc += (neg ? -1 : +1) * (count << shift)`, one step per (input slice, sign bank, weight digit, row fold).
`src/x2c/compiler/x2_pack.py recombine_steps()` produces the step list from a packed layer.

| Piece | File | Check |
|---|---|---|
| operator `x2_acc_step` (one step, combinational) | `src/x2c/verification/rtl_check.py` OPS, reference in `src/x2c/agents/rtl_agent.py` | Yosys eval vs NumPy, 636 vectors (edges incl. 32-bit wrap); A2 can be asked to write it |
| design `x2_recombiner` (clocked, 32-bit acc, read 1 byte at a time) | `hardware/designs/x2_recombiner.v` | Icarus: X2 counts -> outputs == NumPy for conv, depthwise, pointwise, linear |
| on the chip | `x2c build --example x2_recombiner` | 32/36 pins, 227/2160 logic cells, V0 audit exact (5392/5392 bits); nextpnr estimate 21-26 MHz (delay model, not silicon) |

The 1-bit cases use counts produced by the BM Labs X2 behavioral model (the packing logs), so
BM X2 model -> recombiner RTL -> NumPy is checked end to end.

Found while building it: `rtl_check` only read Yosys results printed as `<width>'<bits>`. For 32-bit outputs Yosys
prints fully defined values as plain decimals (`= 2147483647.`), so 337 of 636 results were lost.
`parse_eval_results` reads both forms.

### The other eFPGA operators in the tiny MobileNetV2 graph
| Graph node(s) | Count | Operator | Status |
|---|---|---|---|
| after every X2 layer | 17 | `x2_acc_step` / `x2_recombiner` | built |
| requantise the 32-bit result to INT8 | 17 | `requant_i32_i8` | exists; scale 19/2^10 is ASSUMED, real per-layer scales are not in compiler_graph.json |
| `add` (residual) | 3 | `add8_sat` | exists; saturating INT8 is ASSUMED |
| `flatten` | 1 | none | no logic: only the order of values |
| `pool` | 1 | not built | kind and size are not recorded in compiler_graph.json |
| `shape_preserving` | 27 | not built | kinds are not recorded in compiler_graph.json (in MobileNetV2 usually BatchNorm / ReLU6, unconfirmed) |

## Host bridge: `x2c sim bridge`

### Why a bridge
The fabric's memory is 36 x RAM_32x4 = 4608 bits; one 4-bit-cell tile is 4096 bits of weights. The command stream
from `src/x2c/compiler/x2_pack.py` therefore comes from a host through the pins, and `hardware/designs/x2_bridge.v`
hands it to the X2 block (`RERAM_CIM_32x32`, the chip's own primitive) and returns its results.

| Host pins (30 of 36) | Meaning |
|---|---|
| `cmd_data[11:0]`, `cmd_hi`, `cmd_strobe` | 22-bit command `{all_cols, last, pwm, col, row, mode}` loaded as two 12-bit halves; the second half sends it |
| `cmd_ready` | the previous command was accepted by the X2 |
| `res_valid`, `res_sel[1:0]`, `res_byte[7:0]`, `res_last` | the X2's 21-bit result `{mode, column, count}`, read one byte at a time |
| `res_pop` | consume the result (drives the X2's `RESULT_READY`) |
| `clk`, `rst` | |

X2 settings (`TDC_TIME_OUT`, targets, ...) are parameters of the bridge, i.e. bitstream settings.

### Checks
| Check | Result |
|---|---|
| bridge connects all 58 ports of `RERAM_CIM_32x32` | yes |
| simulation stand-in `hardware/sim/RERAM_CIM_32x32_sim.v` connects the BM Labs macro like `sky130-reram-fpga/src/fabric_wrapper.sv` (l.259-312, 566-624) | same 44 connections |
| host -> bridge pins -> X2 model, the packed conv / depthwise / pointwise / linear layers | every result = X2 golden model; identical line for line to the direct X2 run; rebuilt outputs = NumPy |
| cost of the bridge | conv: 376,514 cycles vs 375,082 direct (+0.4%); programming dominates |
| on the chip (`x2c build --example x2_bridge`) | ok: 30/36 pins, 42 logic cells, 1 of 2 X2 blocks (X20Y6), V0 audit exact (1813/1813 bits, X2 settings included); nextpnr estimate 80-85 MHz (not silicon) |

### Limits
* Only 1-bit cells can be programmed with the chip's commands (SET/RESET). The 4-bit `WRITE_LEVEL` stream has no
  chip command, so it cannot go through the bridge.
* The bridge and the recombiner are separate designs; the engines below join them.
* The host is the testbench here.

### Finding
`sky130-reram-fpga/src/fabric_wrapper.sv` wires a 3-bit X2 error code into the fabric (`EXT_ERROR0..2`, l.259-261), but the Yosys
primitive user designs see declares only `ERROR0`, `ERROR1` (`RERAM_CIM_32x32.v` l.60-61): error bit 2 cannot be read
from fabric logic.

## One-block engine: `x2c sim engine1`

With the bridge alone, every X2 COMPUTE result goes back to the host, which does the shift/sign/add. The engine does
that on the fabric. `hardware/designs/x2_engine.v` takes the packed command stream through the same 12-bit host
port as the bridge, and every COMPUTE count goes straight into an on-fabric 32-bit accumulator (`acc +/- count << shift`,
the recombiner's `x2_acc_step` arithmetic). The host only reads finished partial outputs. Only row folds (layers with more
than 32 inputs per output) are still added on the host.

### How a column finds its accumulator
The packing (src/x2c/compiler/x2_pack.py, chip_x2.place_groups) starts every block on a multiple of CPW columns, so the
column number alone decides everything:

| | formula | 4-bit cells | 1-bit cells |
|---|---|---|---|
| CPW (cells per weight) | 2 * ceil(8 / CELL_BITS) | 4 | 16 |
| accumulators per tile | 32 / CPW | 8 | 2 |
| accumulator | col / CPW | | |
| negative bank | col % CPW >= CPW/2 | | |
| shift | (col % (CPW/2)) * CELL_BITS + slice * SPLIT | SPLIT 4 | SPLIT 8 |

`x2c.commands.sim_engine1.engine_layout` refuses any placement that breaks the alignment.

### Host pins (33 of 36)
clk, rst, cmd_data[11:0], cmd_hi, cmd_strobe, cmd_ready (as in the bridge), slice, acc_clear, idle,
acc_sel[2:0], byte_sel[1:0], acc_byte[7:0]. Host loop per (position, tile): `acc_clear`, then for each input slice set
`slice` and stream the COMPUTE beats, wait for `idle`, read the accumulators byte by byte.

### Results
Simulation (1-bit cells, BM behavioral X2 wired like the chip, 2 positions, seed 2026):

| layer | tiles | reads | cycles | = engine model | output = NumPy |
|---|---|---|---|---|---|
| conv | 4 | 16 | 374493 | yes | yes |
| dw | 4 | 16 | 135202 | yes | yes |
| pw | 8 | 32 | 238518 | yes | yes |
| fc | 5 | 20 | 309281 | yes | yes |

Also PASS with seeds 11, 222, 3333 and 3 positions.

Chip builds (FABulous flow, 12 MHz target, nextpnr estimate):

| design | logic cells | RERAM blocks | Fmax | V0 audit |
|---|---|---|---|---|
| x2_engine (1-bit) | 390 | 1 of 2 | 17.5 MHz | 9592/9592 |
| x2_engine_4bit | 894 | 1 of 2 | 11.2–12.4 MHz (borderline, varies by placement seed) | 22335/22335 |

4-bit is checked for size and timing, and in Python (engine rule rebuilds NumPy exactly), but cannot be simulated
on the chip: the chip's X2 commands only SET/RESET 1-bit cells.

### Finding: clock-to-output race in simulation
The BM behavioral model updates its outputs with blocking assignments at the rising edge. Fabric logic that samples
at the same edge raced it and sometimes missed a result (the pw layer failed). The real macro has a clock-to-output
delay, so `hardware/sim/RERAM_CIM_32x32_sim.v` passes all 32 outputs through `assign #1`. Bridge results are unchanged by it
(identical to the recorded bridge runs).


## Two-block engine: `x2c sim engine2`

A1's fastest schedules program one X2 block while the other computes, but the one-block engine drives only one block.
`hardware/designs/x2_engine2.v` drives both. It has the same column rule, the same command format, and per-block
accumulator banks.

### Pins (35 of 36)
- `clk`, `rst`, `cmd_data[11:0]`, `cmd_hi`, `cmd_strobe`, `acc_clear`
- `cmd_ready[1:0]` and `idle[1:0]`: one each per block, so the host feeds one block while the other is busy
- `acc_sel[3:0]`: bit 3 picks the block's bank for reading and clearing
- `byte_sel[1:0]` and `acc_byte[7:0]`

The high command beat carries the block (`cmd_data[11]`) and the input slice (`cmd_data[10]`) in bits that were unused,
so the old `slice` pin is gone.

### Correctness points
- **Results** from the two blocks can arrive in the same clock. A round-robin arbiter grants one and holds the other
  with `RESULT_READY`. The BM model keeps a result stable until it is accepted (behavioral `.sv` l.365, l.690).
- **Slice of a result:** the slice of the command its block accepted last. The model takes no command while a result
  is pending (`o_ready = !busy && !result_valid`, l.533).
- **Accumulate pipeline:** decode+shift, read, add+write. A result for the accumulator being written in the same clock
  is forwarded; neighbouring columns share an accumulator.

### Measured (BM behavioral X2, 1-bit cells; `x2c sim engine2 --sim`)

| layer | tiles | one block | two blocks | latency cut | predicted cut | model error |
|---|---|---|---|---|---|---|
| conv | 4 | 374,437 | 172,450 | 53.9 % | 53.9 % | ≤ 0.01 % |
| dw | 4 | 135,146 | 68,315 | 49.5 % | 49.5 % | ≤ 0.03 % |
| pw | 8 | 238,406 | 122,496 | 48.6 % | 48.6 % | ≤ 0.04 % |
| fc | 5 | 309,211 | 174,880 | 43.4 % | 43.4 % | ≤ 0.02 % |

- Both layouts reproduce every accumulator (the engine rule) and NumPy exactly.
- "Predicted" is `x2c.compiler.x2_schedule.simulate`, the model A1 uses, fed with each run's exact command counts.
- So A1's two-block assumption is a measured result, not an assumption.

### Chip builds (`x2c build --example x2_engine2` / `x2_engine2_4bit`)

| design | logic cells | X2 | Fmax (nextpnr, 12 MHz target) | V0 audit |
|---|---|---|---|---|
| x2_engine2 (1-bit) | 710 / 2160 | 2 / 2 | 16.7 MHz | 18177/18177 |
| x2_engine2_4bit | 1792 / 2160 | 2 / 2 | 14.5 MHz | 47236/47236 |

The first version failed 4-bit timing at 7.8 MHz: an accumulator multiplexer and a 32-bit adder in one clock. The read
stage with forwarding fixed it. 4-bit is size- and timing-checked only, because the chip's X2 model computes 1-bit cells.

## Real layers end to end: `x2c sim layers`

For each matrix layer of the real tiny MobileNetV2 (shapes from the compiler's IR), it runs IR layer → pack → two-block schedule →
engine → NumPy:
- **4-bit (project setting):** packed and run in Python with the ASSUMED 4-bit cell rule (`count = Σ pwm × level`), then
  compared exactly with NumPy. That rule is the `cell_compute_4bit` entry in `src/x2c/chip/x2_facts.py`, still `missing`,
  because the chip's X2 model has no 4-bit cells.
- **1-bit (what the chip's X2 model computes):** simulated in Icarus on `x2_engine2.v`, all tiles on one block and then
  alternating over both blocks. Every output is compared with NumPy, and measured cycles with the schedule model.
- **Weights:** random INT8, seeded by layer name, because the compiler artifact gives shapes, not trained weights.
  `--weights file.npz` swaps in real ones.
- **Inputs:** random UINT8 patches for `--positions` output positions (a slice of the layer, default 2).
- **Size limit:** layers needing more than `--max-tiles` 1-bit tiles (default 16) are listed as skipped, never silently left out.

## X2 facts and the project clock

| blocks | 2 | model (bel.txt) | hardware_config |

| error_bits_exposed | 2 | model (primitive has ERROR0/1 only) | — |

**To add a number later,** put it in `specifications/x2_overrides.json`; there's no code to edit:
```json
{"program_cycles_per_cell": {"value": 410, "status": "measured", "source": "bench test, chip #3"}}
```
- Every consumer reads `x2_facts.value()`, so the override is used at once, and reports list it as `overridden_by`.
- A malformed file, an unknown name, or a missing status or source is rejected, never ignored.
- A `missing` fact raises `FactMissing`, naming the file to fill in, if anything tries to use it.
- A brand-new kind of fact is one entry in `FACTS`.

### The project clock: 14.0 MHz
This is the highest clock every chip design meets, with a little margin. The repo's nextpnr recipe sets no target of its
own (it only compares against nextpnr's built-in 12 MHz), so the project clock is ours to choose.

| design | nextpnr Fmax |
|---|---|
| x2_engine2_4bit | 14.45 MHz (sets the clock) |
| x2_engine2 | 16.67 |
| x2_engine | 17.51 |
| add8_sat | 42.19 |
| relu8 | 151.52 |

- requant_i32_i8 has no register-to-register path through its hard multiplier, so nextpnr gives it no Fmax.
- The chip chain judges timing against 14.0 MHz, not nextpnr's 12 MHz. A design at 13.9 MHz is UNVERIFIED even
  though nextpnr prints PASS.
- A1's schedules report `latency_us` at this clock: tiny MobileNetV2 is about 3,557,161 cycles ≈ 254 ms per inference
  with the best schedule (an upper bound on programming).
- A faster clock needs the 4-bit two-block engine pipelined further; then change `clock_mhz` (or override it).

### The chip toolchain: `src/x2c/chip/chip_flow.py`
An older Yosys earlier on `PATH` (for example 0.66) fails on the chip's synthesis options (`synth: syntax_error`). So:
- `run_flow` puts the folder of the Python running x2c (the project's `.venv`, with fasm) and
  `~/tools/chip/oss-cad-suite/bin` first on `PATH`, when they exist. `CHIP_PY` and `CHIP_CAD` override them.
- It refuses a Yosys older than 0.70 with a clear message.
- With the suite in `~/tools/chip/oss-cad-suite` (or `CHIP_CAD` pointing at it), no `export PATH=...` line is needed
  before `x2c build`.
